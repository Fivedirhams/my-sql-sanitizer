# CloakDB — Стриминговый анонимизатор SQL-дампов с ИИ-трансформерами

CloakDB — обёртка поверх пользовательских трансформеров для автоматической замены чувствительных данных в MySQL/MariaDB дампах на реалистичные псевдонимы. Обрабатывает файлы **построчно** с нулевым оверхедом памяти и использует LLM API для генерации правдоподобных замен **один раз на колонку**, а не на каждую строку.

## 🏗️ Как это работает: архитектура и фаза маппинга

Весь процесс выполняется внутри одного Python-процесса. Никаких внешних предшагов или промежуточных файлов не требуется.

```
┌──────────────┐     ┌──────────────────┐     ┌────────────────────┐
│ ФАЗА 1       │     │ ФАЗА 2           │     │ ФАЗА 3             │
│ ПРОФИЛИРОВАНИЕ│────▶│ МАППИНГ (ОНЛАЙН) │────▶│ СТРИМИНГ + ЗАМЕНА  │
│ (Сканирование)│     │ (ОДНО вызов к LLM │     │ (О(1) lookup по    │
│               │     │  на колонку!)    │     │  словарю в памяти) │
└──────────────┘     └──────────────────┘     └────────────────────┘
```

### 🔑 Почему есть фаза «Маппинг»? (Ключевое пояснение)

**Маппинг НЕ запускается отдельно.** Он строится **внутри одной команды** при первом взгляде на колонку.

Почему маппинг нужен, если трансформер и так меняет значения? Потому что без него пришлось бы вызывать LLM для **каждой ячейки** (~15 000–500 000 раз). С маппингом: собираем ≤50 уникальных значений на колонку → делаем **1 запрос к LLM** → получаем готовый словарь замен → далее работаем только с ОЗУ.

| Подход | Вызовы LLM | Стоимость | Скорость | Подходит для дампов >500K строк? |
|--------|------------|-----------|----------|----------------------------------|
| Без маппинга (прямая замена каждой ячейки) | N раз × количество строк | Очень дорого | Медленно | ❌ Нет |
| С маппингом (CloakDB) | ~M раз × количество колонок (обычно <50) | Дешево | Мгновенно после загрузки | ✅ Да |

**Как это выглядит на практике:**
1. Скрипт сканирует дамп и видит, что в `Customer.Email` есть 45 уникальных адресов.
2. Отправляет их **все сразу** в LLM одним батч-запросом.
3. Получает JSON: `{"maria@example.com": "elena@demo.org", ...}`.
4. Сохраняет этот словарь в памяти (`transformer._mapping`).
5. При потоковой обработке каждой ячейки делает просто `dict.get(value)` → O(1). Никаких дополнительных сетевых запросов.

После завершения работы скрипта маппинг исчезает. Для офлайн-обработки дампов это проектное решение: не нужно хранить связи оригиналов, гарантируется отсутствие утечек PII.

### 📦 Что такое буферизация и «до 50 уникальных»?
Это не фильтр данных. Это **бюджетный лимит для LLM-вызовов** (`sample_limit: 50` из config.yaml).
- Во время профилирования скрипт собирает уникальные значения колонки до тех пор, пока не наберёт 50 или не закончатся данные в файле.
- Эти значения отправляются в LLM батчами по ≤15 штук (см. ниже секцию Чанкование) для построения маппинга.
- При стриминге **проходят все строки файла**, без ограничений. Если встретится 51-е уникальное значение (или позже в потоке), оно просто не найдётся в словаре и получит fallback-замену.
- **Почему так делают?** LLM-запрос стоит денег и времени. Отправлять 50 000 уникальных email'ов в один чат — дорого и долго. ~50 значений статистически репрезентативны для формирования качественных правил замены.

### 🔄 Доступное объяснение работы трансформеров
Представьте фабрику на конвейере:
1. **Буферизация:** Рабочий останавливает ленту, отбирает первые 20 уникальных деталей на стол, показывает их дизайнеру (LLM). Дизайнер рисует шаблон замены.
2. **Маппинг:** Шаблон распечатывается в виде карточки: `{оригинал_1: замена_1, оригинал_2: замена_2, ...}`. Карточка вешается у станка.
3. **Стриминг:** Лента запускается. Деталь проходит через сканер. Сканер смотрит в карточку. Нашёл точное совпадение → меняет на указанную замену. Не нашёл → ставит заводской штамп `Table_randomhash`. Конвейер не останавливается ни на миг. RAM остаётся чистой, файлы не хранятся, скорость максимальная.

## 🔍 Профайлинг: что анализируется и какие типы поддерживаются

Фаза профилирования (`SQLProcessor._collect_samples`) читает SQL-дамп один раз, извлекает до **20 уникальных значений на каждую колонку** и классифицирует поле.

### Что умеет профайлер
- ✅ MySQL/MariaDB dump format (включая переносы строк в многострочных INSERT)
- ✅ Бэктек-идентификаторы: ``INSERT INTO \`Table\` (\`Col1\`, ...)``
- ✅ Префикс Unicode-строк `N'...'` (автоматическая нормализация)
- ✅ Множественные кортежи на одной строке: `(val1, val2), (val3, val4)`
- ✅ DDL, комментарии, SET/USE/LOCK statements пропускаются без изменений

### Классификация колонок (гибридный автодетект)
Алгоритм `_auto_select_transformer()` определяет тип поля **без использования LLM**, используя комбинацию:
- Паттернов имени колонки (camelCase, snake_case)
- Проверки содержимого сэмплов (наличие `@`, форматов дат, телефонных масок)
- Правил из `config.yaml` (явный маппинг типа → трансформер)

Для нестандартных названий используется ручная настройка в YAML. LLM-классификатор теоретически возможен, но резко увеличивает стоимость и время предварительной обработки.

| Признак | Тип трансформера | Пример колонок |
|---------|-----------------|----------------|
| Содержит `@` | `email` | `Email`, `ContactMail` |
| Цифры ≥7 + паттерн телефонного номера | `phone` | `Phone`, `Fax` |
| Совпадает `%Y-%m-%d` (>70% выборки) | `date_shuffle_year` / `date_shuffle_month` | `BirthDate`, `HireDate` |
| Имена: `FirstName`, `LastName`, `Name` | `name` / `composer` | `Customer.FirstName`, `Track.Composer` |
| Должность: `Title` | `title` | `Employee.Title` |
| Организация: `Company` | `company` | `Customer.Company` |
| Адрес: `Address`, `BillingAddress` | `address` | `Customer.Address`, `Invoice.BillingAddress` |
| Почтовый код: `PostalCode` | `postal_code` | `BillingPostalCode` |
| Локация: `City`, `State`, `Country` | `genre` (циклический swap) | `Customer.City`, `BillingCity` |
| Перечисления: `Genre`, `MediaType`, `Status`, `Stage` | `genre` / `crm_status` | `Genre.Name` |
| PK/FK: заканчивается на `_id` или `Id` | **Пропускается** | `CustomerId`, `InvoiceId` |

## 🛠️ Трансформеры: правила, буферизация и батчинг

Каждый тип данных управляется своим классом-наследником `BaseTransformer`. Они живут в `cloaker/transformers/`.

### Общая схема работы любого трансформера
1. **Буферизация выборки:** При запуске `main.py` собирает ≤20 уникальных значений колонки в RAM.
2. **Загрузка маппинга:** Вызывается `_load_mapping(samples, field_key, stats)`. Либо делает один batch-запрос к LLM, либо строит правило детерминированно.
3. **Стриминг:** При проходе по дампу проверяется `if value in self._mapping: return replacement`. Если нет → хэш-фоллбэк (`Table_hash123`).

### Подробно по каждому типу

| Тип | Источник замен | Правила формирования | Лимит сэмплов | Логика вызова |
|-----|---------------|----------------------|--------------|---------------|
| `name` | LLM | Культурно-адекватные имена того же языка/скрипта. Пол и стиль сохранены. | ≤50 | Чанки ≤15 значений |
| `composer` | LLM | Композиторы/авторы музыки | ≤50 | Чанки ≤15 значений |
| `title` | LLM | Должности схожего уровня (Sales Agent → Client Advisor) | ≤50 | Чанки ≤15 значений |
| `company` | LLM | Организации масштаба/региона | ≤50 | Чанки ≤15 значений |
| `address` | LLM | Улицы, индексы. Гео рандомизируется | ≤50 (длинные) | Чанки ≤15, таймаут до 55s |
| `email` | LLM + статистика | Сохранение доменного распределения | ≤50 | Чанки ≤15 значений |
| `phone` | LLM + регекс | Сохранение country code, формат группировки | ≤50 | Чанки ≤15 значений |
| `postal_code` | LLM + формат | Коды строго по длине/маске | ≤50 | Чанки ≤15 значений |
| `crm_status` | Детерминировано | Цикл: active→inactive→review→active. Распределение сохранено. | До всех | Без LLM |
| `genre` | Детерминировано | Циклическая замена категорий (города, жанры, страны) | До всех | Без LLM |
| `date_shuffle_year` | Детерминировано | Рандомный день/мес в том же году | До всех | Без LLM |
| `date_shuffle_month` | Детерминировано | Рандомный день в том же месяце+году | До всех | Без LLM |

#### 🔌 Буферизация и Батчинг в коде
- **Буфер:** `SQLProcessor._collect_samples()` хранит уникальные значения в RAM. Лимит: `sample_limit: 50` из `config.yaml`.
- **Чанкинг запросов:** `LLMClient._call_api_chunked()` разбивает на чанки ≤15 значений каждый (защита от `max_tokens: 4096` overflow). Таймаут 30–55s, retry ×1 при пустых ответах.
- **Merge результатов:** Результаты каждого чанка объединяются в единый словарь маппинга.

## ✅ Гарантии целостности данных

### 1. Прямые ключи и внешние ссылки (PK/FK)
Колонки, совпадающие с паттернами `*_id` или `Id`/`ID`, **никогда не обрабатываются трансформерами**. Они проходят через pipeline без изменений. Это гарантирует:
- Сохранение автоинкрементных последовательностей (начинаются с 1, без разрывов)
- Корректность foreign key связей между таблицами
- Возможность немедленной повторной загрузки дампа без constraint violations

### 2. Кросс-табличная консистентность
Если одно и то же значение встречается в разных таблицах (например, имя клиента в `Customer` и контакт в `Invoice`), оно всегда заменяется на одинаковый псевдоним благодаря детерминированному хэш-фоллбэку и единому правилу маппинга.

## ⚙️ Конфигурация

### YAML-правила (`config.yaml`)
Переопределяют автодетект для конкретных полей:
```yaml
transforms:
  Artist.Name: name                  # Имя исполнителя → LLM
  Customer.FirstName: name           # Имя клиента → LLM
  Customer.Email: email              # Email → домен+имя сохранение
  Employee.BirthDate: date_shuffle_year  # Дата рождения → год сохраняется
  Genre.Name: genre                  # Жанры → циклический swap
  Track.Composer: composer           # Композитор → LLM
  companies.Inn: skip                # ИНН — пропустить (контрольная сумма!)
  companies.Kpp: skip                # КПП — пропустить
  deals.Stage: crm_status            # Стадии сделок → цикл значений
  payments.Status: crm_status        # Статусы платежей → цикл значений
```

## ⚙️ Чанкование API запросов

### Проблема
Кодик Router API (qwen3.7-flash) имеет ограничение `max_tokens: 4096` на **размер ответа**. 
При отправке >15 уникальных значений в одном запросе JSON-ответ превышает лимит, модель обрезается
на `finish_reason: "length"` → пустой результат → пропущенные записи.

### Решение
**Лимит ≤15 значений на чанк + adaptive splitting по бюджету символов.**

| Параметр | Значение | Описание |
|----------|----------|----------|
| `MAX_VALUES_PER_CHUNK` | 15 | Жёсткий cap — предотвращает overflow max_tokens |
| `chunk_max_chars` | 2500 | Бюджет символов на подзапрос |
| `timeout_base` | 30s | Базовый таймаут на вызов |
| `timeout_max` | 55s | Максимальный таймаут |

**Как это работает:**
1. Клиент разбивает N уникальных значений на чанки по ≤15 штук
2. Каждый чанк шлётся отдельно в LLM с timeout=30-55s
3. Результаты merge-ятся в единый словарь маппинга
4. Пустые/битые ответы retry-атся автоматически (1 повтор)

**Пример для 150 имён артистов:**
```
🔄 Calling LLM (150 values, ~10 chunk(s))...
  [chunk 1/10] 15 values, est 5KB
  [chunk 2/10] 15 values, est 5KB
  ...
  [chunk 10/10] 15 values, est 5KB
  Chunked merge: 150 total entries from 10 chunks
```

### Детерминированные трансформеры (без LLM)

Некоторые поля НЕ требуют вызова LLM — используются локальные алгоритмы:

| Трансформер | Назначение | Алгоритм | Примеры |
|-------------|------------|----------|--------|
| **genre** | Категории/энумы | Циклическая замена | Города, страны, жанры |
| **crm_status** | Бизнес-статусы | Циклическая замена | active→inactive, won→lost |
| **date_shuffle** | Даты | Сохранение формата/распределения | 2024-01-15 → 2019-07-22 |
| **skip** | Игнорировать | Прямое копирование | ИНН, PK/FK IDs, метрики |

**Преимущества:**

## ❓ FAQ

**В: Нужно ли запускать отдельные скрипты перед CloakDB?**  
О: Нет. Вся логика профилирования, маппинга и стриминга интегрирована в `main.py` и выполняется последовательно внутри одной команды.

**В: Где хранится маппинг? Это внешний JSON?**  
О: Маппинг живёт исключительно в оперативной памяти Python-процесса (`transformer._mapping`). После завершения работы удаляется. Это сделано намеренно: для офлайн-дампов хранение映射 оригиналов избыточно и нарушает принцип zero-trust.

**В: Сколько стоит LLM API для большого дампа?**  
О: Цена зависит от количества колонок, требующих LLM-замены (обычно 15–40 на реальную БД). Одна бэтч-вызов ≈ $0.001–0.003. Итого за полный дамп на 1M строк: ~$0.05–0.15. Затраты постоянны, не зависят от行数.

**В: Можно ли добавить свой трансформер?**  
О: Да. Наследуйтесь от `BaseTransformer`, реализуйте `transform()` и `_load_mapping()`, добавьте класс в `TRANSFORMER_MAP` в `__init__.py` и пропишите правило в `config.yaml`.

**В: Что происходит, если LLM недоступен или ответ битый?**  
О: Система не падает. Пустой ответ → фоллбэк на детерминированный хэш-плейсхолдер вида `Customer_a1b2c3d4e5f6`. Повторные попытки запускаются автоматически с экспоненциальной паузой.

**В: Поддерживаете ли PostgreSQL / pg_dump?**  
О: Основная фокусировка на MySQL/MariaDB дампах (поддержка `N'...'`, backticks, многострочных VALUES). PostgreSQL форматы требуют дополнительной адаптации парсера, но архитектура позволяет это реализовать в будущем.
